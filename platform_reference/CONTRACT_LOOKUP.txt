Disk award lookup layout annex

contracts_rolled.parquet remains the analytical source. The optional contracts_lookup.parquet holds identical rows, sorted within bounded original row windows by contract_id and original row ordinal. Part/window order and equal-ID order are retained. Only get_award_profile selects the lookup view; no analytical query is redirected and no table or ART index is materialized.

Build outside the serving process. contract_lookup_layout.py takes one source Parquet file, a new output path, --memory-mb (128–512), --window-rows (default2000000), --temp-root and --report. It uses one query thread and a bounded spill directory, then compares every field and floating-point bit pattern using streaming Arrow. Supervise actual process RSS and disk headroom separately: DuckDB memory_limit is not a whole-process limit. The production rollout rehearsal uses512MB query memory and a768MiB process-RSS stop guard. Do not build this artifact during API startup.

Publish immutable, version-pinned files with content SHA-256, size and ETag. platform_reference.contract_lookup_release.with_contract_lookup accepts complete ordered exact-parity evidence and binds the optional asset to the exact original contracts asset's canonical SHA-256. It refuses unrelated, partial or resource-stopped builds. Copying identical bytes from rehearsal into immutable release storage must retain verified-content lineage.

A layout annex may retain the logical analytical release ID when every original analytical asset is unchanged. Its immutable manifest key/version/SHA and root layout revision differ. stage_main_cache gives the annex a fingerprinted local directory so it and the original layout coexist. Public, Ask and platform-reference manifests stay pinned to the same analytical release. The root remains guarded by the existing serving-graph checks and compare-and-swap promotion/rollback journal.

Each future Main data release needs its own bound lookup build and parity/performance gates. This change does not modify ETL schedules or automatically optimize arbitrary future source releases. A legacy manifest without the optional asset remains supported and uses the original query; a stale lookup from another source fails validation. Reusing an old lookup for fresh data is forbidden. The builder/validator are included in the ETL image definition for release packaging; an updated ETL image must be built before using them in scheduled cloud jobs.

MIMIR_CONTRACT_LOOKUP_ENABLED defaults to1;0 disables use of the optional view. Keep the existing two analytical readers, one reserved indexed point reader,650MB DuckDB memory limit, one query thread, one Uvicorn worker and memory/admission tripwires. A faster disk query does not authorize more reader concurrency.

Before production: complete all-field parity for the exact source generation; real profile DTO, duplicate/missing-ID and old-release tests; distinct-ID timing; mixed analytical/crawl workload; process-memory evidence; immutable originals and guarded rollback rehearsal. Deploy compatible code against the old pointer first, then activate the layout pointer and redeploy. Restore the prior root first if reverting; preserve newer independent source fixes.
